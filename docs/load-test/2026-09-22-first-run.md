## 실행 환경 — 먼저 읽을 것

**목표 환경(Lightsail 2GB)이 아직 없어서 로컬 Docker 스택에 대고 돌렸다.** 따라서:

| 항목 | 계획 | 실제 |
|---|---|---|
| 대상 | Lightsail 2GB staging | 개발 PC의 Docker Desktop (7.4GB 가용, 다른 프로젝트 컨테이너 동시 구동) |
| 발생기 위치 | 대상 밖 별도 머신 | 같은 호스트의 컨테이너 |
| 컨테이너 메모리 한도 | prod override 적용 | **미적용** (base compose) |
| ingress | Cloudflare → Nginx(TLS) | Nginx(HTTP) 직결 |

그래서 **절대 지연·처리량 수치는 Lightsail 예측치로 쓸 수 없다.** 반대로 한도 경계·격리·기능 정확성은
환경과 무관하므로 이 실행으로 확정할 수 있고, 실제로 그쪽에서 버그가 네 개 나왔다.

격리: 별도 compose 프로젝트 `yut-loadtest`(포트 8099, 자체 볼륨)로 띄워 기존 field-test 데이터를
건드리지 않았다. 종료 후 `down -v`로 삭제했다.

## 이 실행에서 찾은 버그 4개

### 1. 고객 상태 조회 IP 한도가 너무 빡빡했다 (분당 20 → 60)

S1에서 VU 2명이 정상 흐름만 돌았는데 429가 35건 났다. 게임 한 번에 상태 조회가 한 번씩 붙으므로
분당 20은 통신사 NAT 뒤 손님 여러 명이 한 IP로 뭉치는 실제 환경에서 정상 손님을 막는다.

- 기본값 60으로 올리고 `app.limits.state-lookup-per-ip-per-minute`로 조정 가능하게 했다.
- 여기서 막아야 하는 것은 손님이 아니라 회수 티켓 행을 쌓는 반복 호출이다.

### 2. 부하 스크립트의 전화번호 생성기가 깨져 있었다

`String(__VU * 100000 + __ITER).padStart(5,"0").slice(-5)` — 끝 5자리를 자르면 VU 성분이 통째로
사라져 모든 VU가 같은 번호를 쓴다. 첫 S3 실행이 **429 0건**으로 "전부 통과"처럼 보였는데, 실제로는
부하 대부분이 게임 생성이 아니라 쿠폰 회수 경로로 새고 있었다.

- 자릿수를 구획으로 나눴다(`010` + RUN 2 + VU 2 + ITER 4).
- 같은 실수가 다시 조용히 숨지 않도록 `revisit_path` 카운터를 추가했다. 새 번호를 쓰는 시나리오에서
  이 값이 크면 한도가 아니라 생성기를 의심해야 한다.

### 3. 안내물 PNG가 PostgreSQL large object로 새고 있었다 (사전 존재 버그)

운영자 화면의 `posterBase64Chars`가 10이라는 말이 안 되는 값으로 나와 파고들었다.

`StorePoster.contentBase64`에 붙은 `@Lob`이 PostgreSQL에서 String을 large object로 매핑해,
컬럼에는 OID 숫자만 들어가고 실제 바이트는 `pg_largeobject`에 따로 살고 있었다. 그 객체는 행을
덮어써도 회수되지 않는다.

실측: 안내물 3회 재생성에 large object 2개 → 5개, 270,668 → 684,032 바이트. **회수되지 않는 +414KB.**
매장 정보를 수정할 때마다 안내물을 다시 만들므로, 2GB VM에서 조용히 차오르는 경로였다.

- `@Lob`을 제거했다. 컬럼은 이미 `columnDefinition="text"`라 DDL 변경이 없다.
- 확인: 안내물 다운로드 200 / 103,340 bytes / PNG 시그니처 정상, 저장값은 base64 원문(137,788자),
  3회 재생성 후 large object **0개**.
- H2 PostgreSQL 모드는 이 차이를 재현하지 못한다. 동작 테스트로는 잡히지 않아 어노테이션 자체를
  잠그는 회귀 테스트를 넣었다(`posterIsStoredInlineSoItCannotLeakLargeObjects`).
- 기존 볼륨 정리: `delete from store_posters;` + `select lo_unlink(oid) from pg_largeobject_metadata;`
  안내물은 파생 데이터라 다음 조회에서 자동 재생성된다.

`GET /api/admin/operator/monitoring`이 실제 PostgreSQL에서 500(`function lo_get(text) does not exist`)
으로 죽던 것도 같은 원인이었다. 안내물 용량 집계를 네이티브 쿼리로 바꿔 함께 고쳤다.

### 4. 고객 단위 잠금 행이 30일을 살아 카운터 테이블이 고객 수만큼 자랐다

용량 실행이 끝난 뒤 `rate_counters`가 8,373행이었다. 내역을 열어 보니 8,367행이 `lock:` 접두사,
만료가 **30일 뒤**였다. 게임 수와 정확히 1:1이다.

잠금은 (매장, 전화번호)마다 하나씩 생기고 요청이 끝나면 더 쓸 일이 없는데 한 달을 살고 있었다.
계획의 목표 규모(50곳 × 30명/일 × 30일 ≈ 45,000)면 `MAX_ROWS=50,000`에 닿고, 그 순간 새 bucket
생성이 fail closed로 막혀 **정상 손님 전원이 429를 받는다.** 출시 한 달 안에 자체 장애가 되는 값이었다.

- `LOCK_TTL`을 1시간으로 줄였다. 동시 요청을 직렬화하기에 충분하고, 정리 주기(10분)가 뒤를 따른다.
  행이 지워져도 다음 요청이 다시 만든다.
- `MAX_ROWS`를 200,000으로 올렸다. 한 행이 200바이트도 안 되니 수십 MB다. 이 숫자가 빡빡하면
  공격이 아니라 정상 트래픽이 먼저 벽에 닿는다.
- 회귀 테스트로 잠금 행의 만료가 `LOCK_TTL` 안에 있는지 잠갔다
  (`customerLockRowsExpireSoTheCounterTableCannotGrowWithCustomers`).

이 버그는 **내가 이번 보안 작업에서 새로 넣은 것**이다. 매장 전체 잠금을 고객 단위로 옮기면서
TTL을 아무 근거 없이 30일로 잡았고, 부하를 걸어 보기 전에는 보이지 않았다.

## 아직 답하지 못한 질문

1. **Lightsail 2GB에서의 실제 지연과 처리량.** 위 수치는 훨씬 큰 개발 머신 것이다.
2. **prod 메모리 한도(backend 768m) 안에서 JVM이 도는가.** 이번 실행은 한도 없이 돌아 JVM이 7.4GB
   기준으로 힙을 잡았다. 768m cgroup에서는 힙이 ~192MB로 잡혀 동작이 달라진다. 반드시 별도 확인.
3. **2시간 soak에서 `rate_counters`와 디스크가 제자리로 돌아오는가.** 잠금 행 TTL을 1시간으로
   줄인 뒤의 실제 정상 상태 행 수는 아직 재지 않았다.
4. **Cloudflare 앞단과 `limit_req` 상호작용.** origin 직결로만 쟀다.
