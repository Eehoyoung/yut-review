# 리브랜딩 및 운영 도메인 전환 계획

> 상태: 2026-09-23 이름·도메인 확정. 서비스명은 `소담한판`, 영문 표기는 `Sodam Hanpan`,
> canonical origin은 `https://hanpan.sodamlabs.kr`이다. Cloudflare DNS와 인증서 범위 확인은 완료했고,
> 운영 서버 배포와 실운영 검증은 미완료다.

## 목표와 변경 원칙

- 제품을 리뷰 도구가 아니라 **매장 참여·재방문 이벤트 운영 도구**로 설명할 수 있는 이름으로 바꾼다.
- 표시명과 운영 도메인은 함께 전환하되, 개발용 localhost와 Quick Tunnel 흐름은 유지한다.
- 고객 QR·쿠폰·게임 링크는 신뢰 가능한 canonical origin에서만 생성한다.
- 기존 `yut.sodamlabs.kr`은 즉시 제거하지 않고 새 주소 검증 뒤 경로·쿼리를 보존해 리디렉션한다.
- DB enum과 동의 증적 키 `YUT_REVIEW`는 표시명이 아니다. 과거 증적 연속성을 위해 별도 데이터
  마이그레이션 결정 없이는 유지하고, 고객에게 보이는 서비스 라벨만 변경한다.
- 결제·정식 가입이 없다는 점은 전환 비용을 낮추지만, 테스트 QR·법률 문서·보안 설정 검증은 생략하지 않는다.

## 6. 변경 영향표와 저장소 반영

다음 범주를 분리해서 변경한다.

1. 표시명: 고객·관리자 UI, 메타데이터, 오류/안내 문구, 이메일·AI 출력 라벨
2. 법률/동의: 약관·개인정보·광고성 문자 동의문과 서비스별 표시 라벨
3. 영업 자산: 소개서, QR 안내물, Groble 초안, 스크린샷
4. 운영 주소: `APP_PUBLIC_ORIGIN`, Nginx `server_name`/forwarded host, 검증 스크립트와 배포 문서
5. 기술 식별자: Java 패키지, Gradle/NPM 이름, DB enum `YUT_REVIEW`

기술 식별자는 외부 표시와 무관하고 변경 위험이 크므로 기본적으로 유지한다. 공개 API 계약이나 DB 증적 키를
바꿔야 할 사유가 생기면 별도 마이그레이션으로 취급한다.

반영 순서:

1. `AGENTS.md`, `CLAUDE.md`, 제품/배포 소스 문서에 새 정체성과 전환 규칙 반영
2. 코드의 표시명·메타데이터·법률 라벨 변경 및 테스트
3. 새 canonical origin을 환경 설정·Nginx·QR/포스터 생성·운영 검증 스크립트에 반영
4. 프런트 lint/test/build와 백엔드 test 실행
5. Docker production-style rebuild 후 localhost/field-test 회귀 확인

## 7. Cloudflare 전환과 출시 검증

Cloudflare MCP에서 확인된 계정 리소스는 현재 `sodamlabs` Worker 1개다. 현재 노출된 MCP 도구에는 DNS
레코드 조회·수정이 없어, MCP로 Workers/공식 문서를 확인하고 DNS·Redirect Rule은 Cloudflare 대시보드
또는 별도 승인된 API 경로에서 실행한다. DNS 현황을 보지 못한 상태에서 레코드를 추측해 만들지 않는다.

2026-09-23 실행 현황:

- Cloudflare DNS에 `hanpan.sodamlabs.kr A 52.79.111.88`, Proxied, TTL Auto를 생성했다.
- Origin Certificate가 `*.sodamlabs.kr`과 `sodamlabs.kr`을 포함하고 2041-09-18까지 유효함을 확인했다.
- 공개 DNS 전파는 확인했으나 새 호스트는 운영 Nginx 배포 전이라 Cloudflare 520을 반환한다.
- 기존 `yut.sodamlabs.kr`은 200을 유지한다. 새 호스트가 200과 핵심 E2E를 통과하기 전에는 기존 주소의
  Redirect Rule을 만들거나 기존 DNS를 제거하지 않는다.
- 운영 서버 SSH 공개키 인증이 없어 이 작업 환경에서는 배포하지 못했다.

무중단 전환 순서:

1. 기존 `yut.sodamlabs.kr` 레코드, 원본 대상, 프록시 상태, SSL 모드, Redirect/WAF 규칙을 캡처한다.
2. 새 호스트를 같은 원본으로 연결하고 Cloudflare 프록시를 사용한다.
3. 새 호스트의 Universal SSL 활성화와 HTTPS 응답을 먼저 확인한다.
4. 새 코드/환경을 배포해 canonical URL, QR, 로그인, API, CSP, HSTS, forwarded headers를 검증한다.
5. 고객 핵심 흐름을 새 호스트에서 실행한다: QR → 이름/전화번호 → 게임 → 쿠폰 → 직원 PIN 사용.
6. 기존 호스트에는 Cloudflare Single Redirect를 사용해 경로와 쿼리를 보존하는 `308` 리디렉션을 둔다.
7. 이전 주소의 QR·북마크·법률 링크가 새 주소로 정확히 이동하는지 확인한다.
8. 최소 관찰 기간 동안 두 호스트의 오류와 인증·쿠폰 흐름을 확인한 뒤 기존 DNS 제거 여부를 결정한다.

Cloudflare 공식 문서상 Single Redirect는 해당 호스트의 DNS가 Cloudflare 프록시 상태여야 한다. HTTP→HTTPS는
Cloudflare `Always Use HTTPS`와 원본 Nginx 리디렉션이 루프를 만들지 않도록 한 계층을 권위 지점으로 정한다.

롤백 조건:

- 새 호스트 TLS 미활성, `/api/actuator/health` 실패, 로그인/QR 절대 URL 오류, CSP 차단,
  고객 핵심 흐름 실패 중 하나라도 발생하면 공개 전환을 중단한다.
- 기존 호스트와 설정을 관찰 기간 동안 유지하고, 새 호스트의 리디렉션을 제거한 뒤 기존 canonical origin으로
  애플리케이션을 되돌린다.
